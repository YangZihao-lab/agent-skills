# Kala-Agent 断舍离示例

> 这是用法示例，不是对 Kala-Agent 当前状态的正式清理结论。执行时仍须读取仓库现状。

## 可能的认知负荷来源

1. README、PROJECT_STATUS、STRATEGY_HANDOFF 等文件可能同时描述阶段，但更新时间和用途不同。
2. 历史研究若以大量活跃分支存在，新窗口需要反复比较。
3. 来源层协议、执行模板、pilot 状态和本地 Control 结果可能分散在多个入口。
4. 工具和协议不断加固后，容易让当前主线被基础设施遮住。

## 适合的处理方式

### KEEP_ACTIVE

- 一个项目入口；
- 一个当前状态真相源；
- 一个当前战略入口；
- 当前正式方法或协议；
- 当前实际执行点。

### MERGE_INTO

重复说明同一当前状态的文档，应由摘要改为引用唯一真相源，避免复制整段状态。

### ARCHIVE

- 已结束的研究路线；
- 已拒绝的 pilot；
- 仅供复现的旧协议；
- 不再参与当前决策的历史分支。

归档必须保留精确引用和证据，不是删除历史。

### DELETE_SAFE

只考虑：

- 可以重新生成的缓存；
- 无引用临时输出；
- 已被 Git 正式版本替代的无价值备份；
- 明确不参与运行和审计的重复文件。

## 不应使用剃刀处理的事项

- 不能因为双遍协议复杂就直接删除协议；是否保留属于项目方法论问题，应先由上级设计窗口裁决。
- 不能删除课程来源证据、冻结 digest 或正式验收记录来让目录更干净。
- 不能把所有历史材料粗暴塞入一个 archive 而不留下可查入口。
- 不能在清理结构时顺便重新设计知识提取方法。

## 人话版输出示例

> Kala-Agent 最耗脑的不是文件总数，而是“当前应该相信哪份状态、哪些历史还需要比较”不够直观。先不要重构代码。第一步只需要统一当前入口，把结束的研究移出默认路径，并保留精确审计引用。这样新窗口不必每次重新读取和比较全部历史，但不会损失证据。
