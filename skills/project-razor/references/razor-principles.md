# Project Razor 原则与检查表

## 1. 简化对象，不简化事实

可以简化入口、结构、命名、流程和维护面；不能通过删除证据、隐藏冲突或抹平未知来制造“简单”。

## 2. 活跃与历史必须分离

项目可以保留丰富历史，但默认工作路径只应暴露当前有效内容。

推荐区分：

```text
active/      当前工作需要
archive/     历史、审计、复现需要
local/       私有、本机、运行时状态
```

不要求所有仓库都采用这些目录名，但必须有等价边界。

## 3. 真相源检查

对每个重要概念询问：

- 当前战略由哪一份文件定义？
- 当前状态由哪一份文件定义？
- 当前运行入口是什么？
- 当前方法或协议由哪一份文件定义？
- 其他文件是引用、摘要还是历史版本？

若不能唯一回答，存在多重真相源。

## 4. 活跃资格检查

一个对象保持活跃至少应满足一项：

- 当前运行直接依赖；
- 当前阶段直接使用；
- 当前决策必须读取；
- 当前测试或安全边界需要；
- 无法从其他受控来源恢复。

否则应考虑合并、归档或删除。

## 5. 删除前检查

- 是否有代码、配置、工作流或动态加载依赖？
- 是否被文档、测试、CI 或发布流程引用？
- 是否包含许可证、审计、证据、迁移或兼容历史？
- 是否可以从 Git 或其他可信来源恢复？
- 是否属于用户明确要求保留的本机状态？
- 删除后是否会让问题更难发现？

任何一项不确定，先标记 `DEFER` 或 `ARCHIVE`。

## 6. 文档剃刀

优先结构：

```text
README / 入口
→ 当前状态
→ 当前设计或协议
→ 专题证据与历史
```

常见处置：

- 重复状态合并到唯一当前状态；
- 旧计划保留为历史，不继续作为入口；
- 摘要只引用真相源，不复制整段内容；
- 过时 README 必须更新或明确标记失效；
- 不用更多索引掩盖已有索引过多。

## 7. 分支与标签剃刀

- 当前开发分支应少而明确；
- 已合并、已放弃或历史研究分支应关闭或转为精确归档引用；
- 保留复现价值前，先记录 lineage 和入口；
- 不把所有历史分支长期留在默认比较范围；
- 不重写需要审计的历史。

## 8. 工具与协议剃刀

每个工具应回答：

- 它现在解决哪个仍然存在的问题？
- 谁在实际调用？
- 有无更简单的现有工具？
- 它的维护成本是否超过当前收益？
- 它属于当前方法论，还是一次实验遗留？

没有当前用途的工具可冻结并归档，不必因“已经开发完成”继续保持活跃。

## 9. 认知负荷检查

让一个不了解历史的新窗口尝试回答：

1. 项目为什么存在？
2. 当前阶段是什么？
3. 当前真正运行的入口是什么？
4. 当前只应读取哪些文件？
5. 下一步由什么决定？

如果必须比较大量分支、旧摘要、多个状态文件或隐含规则，说明结构仍然过载。

## 10. 净减少检查

每个简化方案都要给出：

```text
移除或降级了什么复杂度
新增了什么复杂度
净变化是什么
```

新增一个永久文件来替代五个文件可以成立；新增一个文件但旧文件继续全部活跃，不成立。
