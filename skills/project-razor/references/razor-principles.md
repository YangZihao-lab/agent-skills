# Project Razor 原则与检查表 v0.3

## 1. 每个动作前先问：需要、替代、归宿

任何会新增或长期保留文件、工具、环境、协议、索引、文档或流程的动作，都先回答：

1. **需要**：它直接服务什么目标和主链？没有它，具体阻碍是什么？
2. **替代**：现有对象、通用工具、上游来源或更简单做法能否满足？
3. **归宿**：它是长期资产、阶段支持、证据历史还是一次性产物？谁消费、谁维护、何时退出？

隐式调用时只做这项轻量检查，不自动清理，也不在没有问题时输出长报告。

## 2. 主链资格，而不是年龄、体积或重建资格

保留或删除不能只看文件新旧、大小、是否可重建或是否能搜索到引用。每个对象必须回答：

- 当前服务什么目标；
- 当前和预期长期消费者是谁；
- 不创建或删除后损失什么；
- 已有替代是什么；
- 上游或重建来源是什么；
- 是否有独立证据、审计、许可或迁移价值；
- 最多能证明什么，不能证明什么；
- 生命周期和退役条件是什么。

## 3. 简洁优雅是设计启发式，不是删证据的借口

在同样满足事实、功能、安全和证据边界的方案中，优先：

- 更少独立概念；
- 更少活跃入口和真相源；
- 更少隐藏约定；
- 更强组合性；
- 更容易从上层规则推导下层做法；
- 更小的用户与 AI 心智模型。

真正的简洁不会把复杂度转移给人工记忆、脆弱脚本或不透明约定。简单本身不是正确性的证明。

## 4. 保留生成核，减少平铺派生物

优先保留：

```text
可信上游来源
+ 元规则/方法论
+ 稳定接口与边界
+ 必要代表性示例和测试
```

让大量可推导下层产物按需生成，而不是全部永久保存为独立真相源。

但以下不能仅以“可推导”为由删除：

- 不可约的原始证据；
- 频繁使用的产物；
- 重建昂贵、脆弱或结果不稳定的产物；
- 当前运行直接依赖；
- 用户明确要求保留的材料。

## 5. 简化对象，不简化事实

可以简化入口、结构、命名、流程和维护面；不能通过删除证据、隐藏冲突、抹平未知或删除失败记录制造“简单”。

证明边界必须明确：

```text
文件齐全 ≠ 内容质量可靠
时间轴生成 ≠ 老师思路已提取
教材写完 ≠ Agent 已学会
课程遍历 ≠ 训练有效
测评分数 ≠ 真实迁移能力
```

## 6. 活跃与历史必须分离

当前工作路径只暴露当前有效内容。历史只有在确有审计、迁移、许可证、证据或复现价值时才归档。

`archive/` 不是垃圾桶。没有价值的历史应删除，而不是永久藏起来。

## 7. 一个概念只保留一个活跃真相源

对每个重要概念询问：

- 当前战略由哪一份文件定义？
- 当前状态由哪一份文件定义？
- 当前运行入口是什么？
- 当前方法或教材入口是什么？
- 清理历史由哪一份最小说明记录？
- 其他文件是引用、底稿还是历史版本？

若不能唯一回答，存在多重真相源。

## 8. 职责不同不等于重复

详细底稿与累计入口可以同时保留，只要职责明确：

- 详细底稿用于回到条件、案例和例外；
- 累计入口用于日常读取；
- 两者不能互相伪装成可替代关系。

判断重复看职责，不只看内容是否相似。

## 9. 认知拓扑检查

机器可遍历不等于人易理解。

目录应尽量镜像：

- 上游真实来源结构；
- 用户自然理解的课程、模块或阶段；
- 日常工作路径。

数百个一一对应文件全部放进同一目录，可能物层正确，但事/器层仍然错误。

## 10. 活跃资格检查

一个对象保持活跃至少应满足一项：

- 当前运行直接依赖；
- 当前阶段直接使用；
- 当前决策必须读取；
- 当前测试、安全或证据边界需要；
- 无法从其他受控来源恢复；
- 承担明确且不可替代的底稿或入口职责；
- 是长期反复使用且保留收益高于维护成本的环境或工具链。

否则考虑合并、归档、删除或 `DO_NOT_RECREATE`。

## 11. 长期环境保留检查

环境、模型缓存或工具链满足以下条件时，可以 `KEEP_ACTIVE`：

- 有明确持续消费者；
- 预计反复使用；
- 重建耗时、成本、网络依赖或兼容风险较高；
- 与其他环境不重复，或职责隔离明确；
- 有稳定位置和维护责任；
- 有复核、升级或退役条件；
- 不被误当作知识、证据或完成度。

一次性、无消费者、可可靠重建且任务结束的环境才默认删除。体积大不是充分删除理由。

## 12. 可重建与可删除不是同一件事

可重建只是删除条件之一。

只有同时满足：

- 无当前或合理预期的长期消费者；
- 无独立证据或审计价值；
- 无运行依赖；
- 上游可靠；
- 用户批准；

才可删除。

反过来，已经证明无价值的低质量派生物，即使可重建，也应标为 `DO_NOT_RECREATE`。

## 13. 恢复防火墙

历史文档提到的路径不代表当前存在或应该恢复。

恢复前检查：

- 新的长期消费者是谁；
- 当前最小结构为何不足；
- 最小必要恢复范围是什么；
- 是否会重新引入多重真相源；
- 谁批准恢复。

缺一项，保持 `DO_NOT_RECREATE`。

## 14. 一次性产物默认删除

以下在没有长期消费者时默认属于一次性运行物：

- 临时虚拟环境和批处理环境；
- 缓存、日志、失败重试目录；
- 自动抽帧和候选模型原始输出；
- 临时质量统计、哈希清单和环境 manifest；
- 批处理进度与工作目录；
- 清理用的 admin、清单、快照和脚本。

任务成功后只保留用户指定的最终产物，以及已批准的长期环境和工具链。

## 15. 文档剃刀

优先结构：

```text
README / 入口
→ 当前状态
→ 当前方法或教材
→ 必要底稿与专题证据
→ 一份最小清理决策说明
```

清理决策说明不是当前状态入口，也不是逐文件回滚清单。

## 16. 工具、协议与测评剃刀

每个工具、协议、教材或测评应回答：

- 它现在解决哪个仍存在的问题？
- 谁在实际调用？
- 已有替代是什么？
- 它是否保留了真正需要的信息？
- 它的指标能证明到哪一层？
- 它的生命周期和退役条件是什么？
- 维护成本与认知成本是否超过收益？

没有当前用途、不能证明下游能力、或诱导 AI 误判进度的结构，不应因沉没成本继续活跃。

## 17. 认知预算检查

每个长期对象都会要求用户和未来 AI 记住：

- 它是什么；
- 为什么存在；
- 与其他对象的区别；
- 何时使用；
- 谁维护；
- 何时退出。

因此要同时衡量磁盘成本和认知成本。新增对象必须说明它让哪些旧概念、入口或维护动作退出。

## 18. 净减少检查

每个简化或新增方案都要给出：

```text
移除或降级了什么复杂度
新增了什么复杂度
清理本身留下什么
长期需要多记住什么
净变化是什么
```

新增一个永久文件替代五个文件可以成立；新增一个管理系统而旧结构继续存在，不成立。

## 19. 新窗口测试

让不了解历史的新窗口回答：

1. 项目为什么存在？
2. 当前阶段是什么？
3. 当前最短主链是什么？
4. 当前真正入口是什么？
5. 哪些文件最多只能证明低层准备完成？
6. 哪些长期环境为什么保留？
7. 哪些已删除结构不得重建？
8. 最小生成核是什么？
9. 下一步由什么决定？

若必须比较大量历史方案、旧分数、多个索引或隐含规则，结构仍然过载。
