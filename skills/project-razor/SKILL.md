# Project Razor：项目断舍离与剃刀

## 目的

本 Skill 的目标不是把仓库变得“看起来整齐”，而是：

> 用最少、最清楚、足以支持当前主链的结构，降低用户和 AI 理解、决策与维护项目时的负担。

它既是一把清理旧结构的刀，也是一道在每次新增之前运行的轻量护栏。真正有效的断舍离不是等项目膨胀后再大扫除，而是在每一个动作前先问：

1. **真的需要吗？**
2. **已有替代品吗？**
3. **最后如何处理？**

它不通过隐藏事实制造简单，也不会为了整理项目再建设一套更复杂的整理系统。

## 默认开启，但默认不打扰

本 Skill 允许隐式调用。隐式调用时只运行 `PRE_ACTION_RAZOR`：

- 不移动、合并、归档或删除任何内容；
- 不自动发起大型清理；
- 不要求每个普通动作都输出长报告；
- 若检查不改变当前动作，可以静默通过；
- 只有发现明显的重复、长期负担、生命周期缺失或更简单替代时，才用人话提醒；
- 所有实际清理和恢复仍需用户明确批准精确动作。

显式调用 `$project-razor` 时，才进入完整结构审计、清理计划、执行或恢复审查。

## 与分层治理的分工

`layered-thinking-governance` 负责回答：

- 最初目标是什么；
- 当前问题属于哪一层；
- 当前最短主链是什么；
- 允许生成什么；
- 最多能证明什么；
- 何时停止；
- 当前窗口是否有权改变方法论或战略。

`project-razor` 在已经批准的方向和范围内回答：

- 这个新东西是否真的需要；
- 是否已有更简单的替代；
- 它应是长期资产还是一次性产物；
- 哪些文件、工具、环境和流程真正服务主链；
- 哪些应保持活跃、合并、归档、删除或禁止重建；
- 怎样让新窗口更少读取、更少比较、更少记忆。

核心关系：

> **分层治理负责不要在错误层级上努力；Project Razor 负责在每个动作中，只引入和保留服务主链的最小结构。**

刀不能自己决定项目方向。若清理或拒绝新增需要改变术或法，必须上报。

## 八条基本原则

### 1. 当前主链优先

任何新增或活跃的文件、分支、工具、环境或协议都必须回答：

1. 它现在服务什么目标？
2. 谁把它当作运行入口、证据、教材或真相源？
3. 不创建或删除后具体损失什么？
4. 能否使用现有工具、上游来源或更简单结构替代？
5. 它最多能证明什么，不能证明什么？

“以前投入很多”“文件很多”“以后也许有用”不能单独构成新增或活跃保留理由。

### 2. 需要—替代—归宿

在创建、安装、购买式引入或长期保留任何对象前，执行三问：

- **需要**：它是否直接服务当前目标和主链？没有它，具体阻碍是什么？
- **替代**：已有文件、工具、环境、通用能力或上游来源能否满足？能否复用而不是新增？
- **归宿**：它属于长期资产、阶段性支持、证据历史还是一次性产物？谁维护？何时复核、替换或删除？

没有明确归宿的长期对象，不应默认进入活跃结构。

### 3. 一个概念只保留一个活跃真相源

同一个概念不应同时由多份文件竞争解释，例如多个当前状态、战略入口、执行协议、总索引和完成度报告。

历史材料只有在确有证据、审计、迁移或复现价值时才归档；没有价值的历史不应仅因为“舍不得删”进入永久 archive。

### 4. 简化对象，不简化事实

可以简化入口、结构、命名、流程和维护面；不能通过删除证据、隐藏冲突、抹平未知或删掉失败结果来制造“简单”。

同时必须防止证明层级偷换：

```text
文件齐全
≠ 内容质量可靠
≠ 分析过程已提取
≠ 教材已经学会
≠ Agent 能力已经形成
```

### 5. 简洁优雅与生成核

用户确认的设计偏好是：在同样满足事实、功能、安全和证据边界的方案中，优先选择更简洁、优雅、生成性更强的结构。

“简洁”不是字数少或文件少，而是：

- 独立概念和例外更少；
- 活跃入口和真相源更少；
- 规则之间可组合；
- 一个上层规则能推导多个下层做法；
- 新窗口能用更小的心智模型理解并继续工作；
- 没有把复杂度偷偷转移到隐藏约定、人工记忆或脆弱脚本中。

优先保留**生成核**：

```text
可信上游来源
+ 少量元规则/方法论
+ 稳定接口与边界
+ 必要代表性示例和测试
→ 按需推导或重建下层产物
```

但生成性不能替代不可约的原始证据，也不能成为删除高频、昂贵、脆弱或结果不稳定产物的借口。简洁优雅是一项设计启发式，不是“简单就一定真实”的证明。

### 6. 长期环境可以保留

环境体积大或理论上可重建，不等于应该删除。

长期使用的环境、模型缓存或工具链可以标记为 `KEEP_ACTIVE`，只要它：

- 有明确的当前和长期消费者；
- 被反复使用，而非仅服务一次任务；
- 重建耗时、成本、网络依赖或兼容风险较高，保留具有实际收益；
- 与其他环境不重复，或隔离职责明确；
- 有稳定位置、维护责任和复核/退役条件；
- 不被误当作知识、证据或项目成果。

默认删除的是**一次性、无当前消费者、可可靠重建且任务已经结束**的环境和运行物，而不是所有可重建环境。

### 7. 可逆优先，但不迷信保留

不确定时优先：

```text
活跃 → 合并 → 归档 → 删除
```

但归档不是垃圾桶。若对象满足：

- 可从可信上游重建；
- 没有当前消费者；
- 没有独立证据、审计或许可证价值；
- 没有运行依赖；
- 用户明确批准；

则应直接删除，而不是制造永久鸡肋。

### 8. 净减少与认知预算

人的大脑和新 AI 窗口都无法无成本地容纳无限文件、规则、工具和历史。每个长期对象都会占用认知预算，即使磁盘空间几乎免费。

新增目录、索引、清单、审计报告、治理文件或环境时，必须说明：

- 它替代了什么；
- 它新增了哪些需要长期记忆和维护的概念；
- 用户和 AI 因此少记住了什么；
- 总认知负荷是净减少、净不变还是净增加。

> 不能用“再加一份总览”解决“总览太多”。

清理本身产生的 admin、逐文件回滚清单、哈希账本、临时脚本和工作目录，在任务结束后默认删除。大型清理最多保留一份人话决策记录，且它不是当前状态入口。

## 删除后恢复必须重新举证

历史文档提到已删除路径，只证明过去存在，不代表应该恢复。

对被标记为 `DO_NOT_RECREATE` 的结构，恢复前必须同时证明：

- 存在新的明确长期消费者；
- 当前最小结构无法满足；
- 恢复范围是最小必要范围；
- 上层方法或目标允许；
- 用户明确批准。

不得因旧文档、旧分数、旧任务或技术上“可以重建”就自动复活整套旧流水线。

## 断、舍、离、剃刀

- **断**：在新增前阻断不必要、重复、无归宿的长期结构。
- **舍**：合并重复内容，删除可再生且无消费者的派生物。
- **离**：不因沉没成本执着于旧教材、旧测评、旧工具和旧流程。
- **剃刀**：在同样满足目标的方案中，选择假设更少、入口更少、维护面更小、生成性更强的方案。

## 处理范围

本 Skill 可审查：

- 即将创建、安装或长期保留的新对象；
- 顶层目录和默认入口；
- README、状态、战略、交接和设计文档；
- 活跃分支、历史分支与 tags；
- 重复脚本、工具、协议和工作流；
- 生成物、缓存、备份、失败重试和过期 fixture；
- 虚拟环境、批处理环境、模型输出和一次性工作目录；
- 多个相互竞争的配置、索引或真相源；
- 需要用户或 AI 同时记住的隐含规则；
- 已删除但被历史文档诱导重建的旧结构。

默认不审查用户未指定的其他仓库，也不跨仓库大范围清理。

## 七种处置结果

每个候选项必须被归入以下一种：

- `KEEP_ACTIVE`：当前主链仍直接需要，包括满足长期环境资格的对象。
- `MERGE_INTO`：内容有价值，但应并入指定的唯一真相源。
- `ARCHIVE`：确有历史、证据、迁移或复现价值，但不应出现在默认工作路径。
- `DELETE_SAFE`：可安全删除，且不损害运行、证据、许可和恢复能力。
- `DEFER`：证据不足，暂不处理。
- `DO_NOT_TOUCH`：当前受保护，禁止改动。
- `DO_NOT_RECREATE`：已经删除或退出活跃路线；除非重新满足恢复门禁，否则未来 AI 不得重建。

`DO_NOT_TOUCH` 保护当前存在的对象；`DO_NOT_RECREATE` 阻止旧结构重新回到活跃路径。

## 使用模式

### PRE_ACTION_RAZOR

隐式默认模式。在任何会新增或长期保留结构的动作前，快速检查：

```text
NEED：真的需要吗？
ALTERNATIVE：已有替代吗？
DESTINATION：最后如何处理？
GENERATIVE_CORE：能否保留更小的生成核而不是整套派生物？
COGNITIVE_COST：它会让用户和 AI 多记住什么？
```

合法结论：

- `USE_EXISTING`：使用现有对象，不新增。
- `CREATE_TEMPORARY`：可以创建，但必须指定一次性目录和删除时点。
- `CREATE_PERSISTENT`：可以长期保留，但必须指定消费者、职责和退役条件。
- `REJECT_ADDITION`：价值不足或存在更简单替代，不创建。
- `ESCALATE`：是否新增涉及术或法，交由上层或用户决定。

该模式不得自动删除，也不得把普通任务改造成完整清理项目。

### QUICK_RAZOR

快速指出最影响理解的 3～5 个复杂度来源，不修改项目。

### STRUCTURE_AUDIT

建立当前活跃路径，识别：

- 当前唯一入口是否明确；
- 同一概念是否有多个真相源；
- 历史材料是否混在活跃路径；
- 哪些结构需要用户长期记忆；
- 哪些工具只解决已经不存在的问题；
- 目录是否符合用户理解项目的自然结构；
- 哪些一次性产物正在假装成长期资产；
- 哪些长期环境具有真实消费者，应该保留；
- 当前是否保留了可推导大多数下层产物的生成核。

### CUT_PLAN

生成精确的断舍离计划，但不执行。每个动作必须包含：

- 目标路径或对象；
- 当前作用和当前消费者；
- 建议处置；
- 理由；
- 已有替代；
- 生命周期和退出方式；
- 上游或重建来源；
- 依赖检查；
- 证据价值；
- 风险；
- 回滚方式；
- 未来重建策略；
- 预期减少的认知负荷。

### APPLY_APPROVED

只有用户明确批准完整动作清单后才能执行。

执行要求：

1. 清理前记录 Git 状态和必要基线；
2. 不把功能开发和结构清理混在同一任务；
3. 先改引用和入口，再移动或删除；
4. 一次性环境、脚本和工作目录默认在成功后删除；
5. 已批准的长期环境按其消费者和退役条件保留；
6. 清理后运行相关测试、链接、目录和主链校验；
7. 报告实际删除、合并、归档和保留内容；
8. 不扩大到未批准范围。

### FINALIZE_CLEANUP

大型清理结束后：

- 删除本次清理制造的临时 admin、清单、快照、脚本、一次性环境和日志；
- 不删除已确认长期使用、具有当前消费者的环境；
- 若未来 AI 确实需要知道删除历史，只保留一份最小人话说明；
- 该说明只记录删除类别、原因、上游是否仍在、保护边界和 `DO_NOT_RECREATE`；
- 不创建逐文件回滚账本；
- 不把清理说明变成当前状态或任务入口；
- 当前状态仍由项目唯一状态文件定义。

使用 `templates/cleanup-decision-record.md`。

### RESTORE_REVIEW

当 AI 想恢复历史路径、旧教材、旧测评、旧协议或旧环境时，先检查恢复门禁。

默认结论是 `DO_NOT_RECREATE`，除非存在新的消费者、当前结构不足、最小恢复范围和用户批准。

### POST_CUT_VERIFY

检查清理后：

- 项目主链仍可运行和验证；
- 活跃入口没有断链；
- 当前状态和战略来源仍唯一；
- 需要保留的证据仍可精确定位；
- 目录分组符合用户自然理解，而不只是文件物理齐全；
- 一次性清理系统和工作目录已经移除；
- 长期环境仍可供其消费者使用；
- 新结构实际减少了新窗口读取范围；
- 已删除结构没有被自动重建；
- 输出能够说明其最大证明范围；
- 简化没有把复杂度转移成隐藏约定。

## 推荐工作流

### 第一步：每个动作前先过微型剃刀

对任何新增或长期保留动作，先回答：

```text
真的需要什么
→ 已有什么替代
→ 临时还是长期
→ 当前消费者是谁
→ 最终如何退出
→ 能否只保留生成核
→ 会增加多少认知负担
```

### 第二步：固定主链和证明上限

开始完整清理前明确：

```text
最初目标
→ 当前层级
→ 最短主链
→ 必须保留的输入与证据
→ 允许留下的长期产物
→ 最大可证明范围
→ 停止条件
```

### 第三步：画出最小活跃结构

回答新窗口继续项目时最少需要读取什么：

```text
入口 → 当前状态 → 当前方法/教材 → 必要详细底稿 → 当前执行点
```

默认路径之外的材料必须说明为什么仍需活跃。

### 第四步：检查认知拓扑与生成核

目录结构不仅要机器可遍历，还要符合用户理解项目的自然分组。

例如，数百个文件全部放进一个目录，可能在物层上“一一对应”，但会破坏用户对课程、模块或阶段的整体认识。优先镜像真实来源结构或用户工作模型。

同时检查能否用少量上游、元规则、接口和代表性测试推导大量下层产物，避免把每个可推导结果都永久保存为独立真相源。

注意：内容相同才可能重复；两个文件若分别承担“详细底稿”和“日常累计入口”，职责不同，可以同时保留。

### 第五步：按风险从低到高处理

建议顺序：

1. 断：停止继续新增重复或无归宿结构；
2. 修正失效链接和过时入口；
3. 合并重复真相源；
4. 删除可再生缓存、备份、一次性环境和无消费者生成物；
5. 保留具有长期消费者和明确退役条件的环境；
6. 只把确有价值的历史移出活跃路径；
7. 删除已经失去用途的旧教材、测评、协议和管理层；
8. 最后才进行目录重构或高风险删除。

### 第六步：清理清理系统本身

任务完成后只保留用户指定的最终产物。清理过程中的：

- admin 目录；
- 逐文件清单；
- relocation manifest；
- 哈希审计；
- 回滚快照；
- 一次性脚本；
- 一次性环境；
- 缓存和日志；

默认删除，除非有明确长期消费者。

### 第七步：验证净收益

清理方案必须回答：

- 用户以后少记住了什么？
- AI 新窗口少读取了什么？
- 当前状态少经过了几个入口？
- 哪些维护动作被取消？
- 目录是否更符合用户的自然理解？
- 是否保留了真正需要的长期环境？
- 是否留下了足够小而有生成力的核心？
- 是否引入了新的隐藏规则或永久治理负担？
- 哪些被删除的内容被标记为不得重建？

如果无法说明净收益，不执行。

## 认知负荷与质量指标

不设置机械固定上限，但至少比较：

- 顶层活跃入口数量；
- 同一概念的权威文件数量；
- 活跃分支数量；
- 找到当前状态需要跳转的次数；
- 重复描述同一流程的文档数量；
- 日常工作必须同时理解的工具和协议数量；
- 新窗口需要比较的历史方案数量；
- 一次性环境、脚本和运行物是否长期滞留；
- 长期环境是否有明确消费者和退役条件；
- 目录结构是否反映用户自然分组；
- 能否从较小生成核推导多数下层结构；
- 文件覆盖率是否被误当成内容质量或能力证据。

这些指标用于比较清理前后，不用于追求漂亮数字。

## 必须保留的边界

不得为了简化而破坏：

- 外部或上游原始来源；
- 来源与证据链；
- 合法合规和许可证文件；
- 数据库迁移与兼容历史；
- 当前运行所需的隐式入口；
- 用户明确保留的未跟踪或私有本地材料；
- 真正需要的详细底稿和日常入口；
- 已确认长期使用的环境、模型缓存和工具链；
- 尚未解决的冲突和未知信息。

“把问题藏起来”不算简化。

## 输出格式

隐式 `PRE_ACTION_RAZOR` 默认只在需要改变动作时简短输出：

1. 是否真的需要；
2. 可用替代是什么；
3. 建议的生命周期和最终归宿；
4. 是否会增加长期认知负担；
5. 建议动作。

完整审计时，先用人话输出：

1. 项目目前最耗脑的地方是什么；
2. 当前最短主链是什么；
3. 哪三项最值得先处理；
4. 处理后用户和 AI 会少记住什么；
5. 哪些东西明确不能动；
6. 哪些长期环境应保留；
7. 哪些删除项未来不得重建；
8. 当前只是在审计、计划，还是已获准执行。

然后再输出处置表、路径、消费者、替代、生命周期、上游、依赖、测试、回滚和恢复门禁。

详细模板见 `templates/razor-report.md`。

## 反模式

- 每个动作都输出冗长剃刀报告，反而增加认知负担。
- 为了整理再增加多个索引、状态文件和 admin 层。
- 只因代码搜索不到引用就删除动态加载内容。
- 把所有东西都移到 `archive/`，却不判断是否真有历史价值。
- 让清理临时文件永久留在仓库。
- 因为环境体积大或可重建，就删除仍被长期使用的环境。
- 一次同时清理多个仓库。
- 清理过程中顺便重写功能或方法论。
- 因为旧方案投入很多就永久保持活跃。
- 因为技术上可以重建，就自动恢复已经证明无价值的旧流水线。
- 为了目录好看而增加理解和运行成本。
- 把文件数量、覆盖率、旧分数或纠错条数当成能力成果。
- 删除上游原始来源，却保留低质量派生物。
- 用“生成核”作为删除不可约证据或高频昂贵产物的借口。
