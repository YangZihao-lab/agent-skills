# Project Razor：项目断舍离与剃刀

## 目的

本 Skill 的目标不是把仓库变得“看起来整齐”，而是：

> 用最少、最清楚、足以支持当前目标的结构，降低用户和 AI 理解、决策与维护项目时的负担。

它优先减少复杂度，不会为了整理项目再建设一套更复杂的整理系统。

## 四条基本原则

### 1. 当前目的优先

任何活跃文件、分支、工具或协议都必须能说明：

- 它当前服务什么目标；
- 谁把它当作入口或真相源；
- 删除或归档后具体会损失什么。

“以前投入很多”“以后也许有用”不能单独构成活跃保留理由。

### 2. 一个概念只保留一个活跃真相源

同一个概念不应同时由多份文件竞争解释，例如多个当前状态、多个战略入口、多个执行协议。

允许保留历史材料，但必须移出默认活跃路径，并明确标记为归档。

### 3. 可逆优先

不确定是否应删除时，优先：

```text
活跃 → 合并 → 归档 → 删除
```

只有可重新生成、无审计价值、无运行依赖且用户明确批准的内容，才进入删除候选。

### 4. 净减少原则

新增目录、索引、清单或治理文件时，必须说明它替代了什么，并使总认知负荷净减少。

不能用“再加一份总览”解决“总览太多”。

## 断、舍、离、剃刀

- **断**：停止继续增加当前不需要的分支、工具、协议和文档层。
- **舍**：合并重复内容，把历史材料归档，删除可安全再生的杂物。
- **离**：不因沉没成本执着于旧方案；允许停止维护已经失去当前用途的结构。
- **剃刀**：在同样满足目标的方案中，选择假设更少、入口更少、维护面更小的方案。

## 处理范围

本 Skill 可审查：

- 顶层目录和文件入口；
- README、状态、战略、交接和设计文档；
- 活跃分支、历史分支与 tags；
- 重复脚本、工具、协议和工作流；
- 生成物、缓存、备份和过期 fixture；
- 多个相互竞争的配置或真相源；
- 需要用户或 AI 同时记住的隐含规则。

默认不审查用户未指定的其他仓库，也不跨仓库大范围清理。

## 五种处置结果

每个候选项必须被归入以下一种：

- `KEEP_ACTIVE`：当前仍是必要的活跃结构。
- `MERGE_INTO`：内容有价值，但应并入指定真相源。
- `ARCHIVE`：需要保留历史、证据或复现价值，但不应出现在默认工作路径。
- `DELETE_SAFE`：可安全删除，且不损害运行、审计、许可和恢复能力。
- `DEFER`：证据不足，暂不处理。
- `DO_NOT_TOUCH`：许可证、证据链、迁移历史、隐私边界或其他原因禁止改动。

不得用模糊的“可能没用”作为删除理由。

## 使用模式

### QUICK_RAZOR

快速指出最影响理解的 3～5 个复杂度来源，不修改项目。

适合：用户只想迅速知道“哪里最乱”。

### STRUCTURE_AUDIT

建立当前活跃路径，识别：

- 当前唯一入口是否明确；
- 同一概念是否有多个真相源；
- 历史材料是否混在活跃路径；
- 哪些结构需要用户长期记忆；
- 哪些工具只解决已经不存在的问题。

### CUT_PLAN

生成精确的断舍离计划，但不执行。每个动作必须包含：

- 目标路径或对象；
- 当前作用；
- 建议处置；
- 理由；
- 依赖检查；
- 风险；
- 回滚方式；
- 预期减少的认知负荷。

### APPLY_APPROVED

只有用户明确批准完整动作清单后才能执行。

执行要求：

1. 清理前记录 Git 状态和必要基线；
2. 不把功能开发和结构清理混在同一任务；
3. 先改引用和入口，再移动或删除；
4. 清理后运行相关测试、链接或目录校验；
5. 报告实际删除、合并、归档和保留内容；
6. 不扩大到未批准范围。

### POST_CUT_VERIFY

检查清理后：

- 项目仍能运行和测试；
- 活跃入口没有断链；
- 当前状态和战略来源仍唯一；
- 历史证据仍可精确定位；
- 新结构确实比旧结构更容易理解。

## 推荐工作流

### 第一步：先确定不能丢的东西

开始清理前先明确：

- 项目当前目标；
- 正式运行入口；
- 当前真相源；
- 必须保留的证据、历史和许可证；
- 用户明确要求保留的本地状态。

### 第二步：画出最短活跃路径

回答一个新窗口或新开发者继续项目时，最少需要读取什么：

```text
入口 → 当前状态 → 当前方法/协议 → 当前执行点
```

默认路径之外的材料，应说明为什么仍需保持活跃。

### 第三步：按风险从低到高处理

建议顺序：

1. 停止继续新增重复结构；
2. 修正失效链接和过时入口；
3. 合并重复说明；
4. 把历史材料移出活跃路径；
5. 删除可再生缓存、备份和无引用生成物；
6. 最后才进行目录重构或高风险删除。

### 第四步：验证净收益

清理方案必须回答：

- 用户以后少记住了什么？
- AI 新窗口少读取了什么？
- 决定当前状态少经过了几个入口？
- 哪些维护动作被取消？
- 是否引入了新的隐藏规则？

如果无法说明净收益，不执行。

## 认知负荷指标

不设置机械的固定上限，但至少观察：

- 顶层活跃入口数量；
- 同一概念的权威文件数量；
- 活跃分支数量；
- 找到当前状态需要跳转的次数；
- 重复描述同一流程的文档数量；
- 日常工作必须同时理解的工具和协议数量；
- 新窗口需要比较的历史方案数量。

这些指标用于比较清理前后，不用于追求漂亮数字。

## 与 layered-thinking-governance 的关系

`project-razor` 主要处理器、事、物层的复杂度，也可以向术层提出简化建议。

它不能自行改变项目最终目标或战略思维方式。若清理需要改变方法论或战略，应上报 `layered-thinking-governance` 对应的上级窗口裁决。

## 必须保留的边界

不得为了简化而破坏：

- 来源与证据链；
- 合法合规和许可证文件；
- 数据库迁移与兼容历史；
- 当前运行所需的隐式入口；
- 用户明确保留的未跟踪或私有本地材料；
- 可复现实验需要的精确冻结引用；
- 尚未解决的冲突和未知信息。

“把问题藏起来”不算简化。

## 输出格式

每次先用人话输出：

1. 项目目前最耗脑的地方是什么；
2. 哪三项最值得先处理；
3. 处理后会少记住什么；
4. 哪些东西明确不能动；
5. 当前只是在审计、计划，还是已获准执行。

然后再输出处置表、路径、依赖、测试和回滚细节。

详细模板见 `templates/razor-report.md`。

## 反模式

- 为了整理文档再增加多个索引和状态文件。
- 只因代码搜索不到引用就删除动态加载内容。
- 把历史证据和当前入口一起删除。
- 一次同时清理多个仓库。
- 清理过程中顺便重写功能。
- 因为旧方案投入很多就永久保持活跃。
- 为了目录好看而增加理解和运行成本。
- 把所有东西都移到 `archive/`，却不明确当前唯一入口。

## 调用示例

```text
$project-razor

对当前仓库执行 QUICK_RAZOR，只读，告诉我最影响理解的五个复杂度来源。
```

```text
$project-razor

审查当前项目的文档、分支和工具结构，生成 CUT_PLAN，不做任何修改。
```

```text
$project-razor

只执行我已批准的第 1、2 项清理，不得扩大范围；完成后运行 POST_CUT_VERIFY。
```
